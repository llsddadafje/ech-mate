## 1. 状态机在项目中做什么

状态机协调启动、唤醒、录音、等待回复、播放、故障和停止这些阶段。它根据“当前状态 + 发生的事件”查找下一状态，再执行旧状态的退出动作和新状态的进入动作。

```text
各模块检测到事情发生
        ↓
把 AppEvent 的整数编号放入 eventQueue_
        ↓
Application 的状态线程取出事件
        ↓
HandleEvent()：查 transitions_，确定下一状态
        ↓
ChangeState()：旧状态 Exit() → 更新状态 → 新状态 Enter()
```

状态切换规则集中在 [StateConfig.cc 第42行起](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/StateConfig.cc:42)，事件处理线程在 [Application.cc 第35行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/Application.cc:35)。

直接调用切换函数也可以设计出状态机。本项目使用事件队列，是为了让网络回调、唤醒检测线程、播放结束检查线程只负责上报事件，由状态线程统一执行切换。`AppEvent` 枚举本身不会自动调度线程或调用函数。

## 3. 两张表分别保存什么

定义在 [StateMachine.h 第68行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.h:68) 和 [第83行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.h:83)：

```cpp
std::unordered_map<int, std::pair<EnterFunc_t, ExitFunc_t>> stateActions_;
std::unordered_map<int, std::unordered_map<int, int>> transitions_;
```

`unordered_map` 是通过键查找值的哈希表容器。它利用哈希函数定位存储区域，再比较键找到对应项；不同键可能发生哈希冲突。键可以不连续，遍历顺序也不保证按大小或插入顺序排列。

`pair` 把两个值放在一起，通过 `.first`、`.second` 访问。它不是另一张哈希表。

| 表 | 外层键 | 外层值 | 解决的问题 |
| --- | --- | --- | --- |
| `stateActions_` | 状态编号 | 一对进入、退出回调 | 进入或退出这个状态时执行什么函数？ |
| `transitions_` | 当前状态编号 | 一张“事件编号 → 目标状态编号”的内层表 | 当前状态遇到这个事件后，切换到哪里？ |

### 3.1 stateActions_：状态编号对应两个回调

回调类型定义在 [StateMachine.h 第8行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.h:8)，都是 `std::function<void()>`。

[StateConfig.cc 第37行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/StateConfig.cc:37) 注册播放状态：

```cpp
state_machine.RegisterState(
    static_cast<int>(AppState::speaking),
    [app]() { SpeakingState::Enter(app); },
    [app]() { SpeakingState::Exit(app); }
);
```

[StateMachine.cc 第27行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.cc:27) 保存两个回调：

```cpp
stateActions_[state] = std::make_pair(on_enter, on_exit);
```

因此，`stateActions_[6].first` 是进入回调，`stateActions_[6].second` 是退出回调。加上 `()` 才会执行：

```cpp
stateActions_[6].first();  // 调用 SpeakingState::Enter(app)
stateActions_[6].second(); // 调用 SpeakingState::Exit(app)
```

注册时保存的是lambda；lambda内部的 `Enter/Exit` 当时还没有被执行。

### 3.2 transitions_：一张外层表，每个状态对应一张内层表

```text
transitions_
└─ 当前状态编号
   └─ 一张内层表
      ├─ 事件编号A → 目标状态编号A
      ├─ 事件编号B → 目标状态编号B
      └─ ……
```

一个状态对应一张内层表，多个的是这张表中的规则条目。

例如，`idle` 对应的内层表内容相当于以下初始化列表（内容示意，不是另外执行一遍注册）：

```cpp
{
    {0, 0}, // fault_happen → fault
    {3, 2}, // to_stop → stopping
    {4, 6}  // wake_detected → speaking
}
```

这里 `{4, 6}` 的 `4` 是事件编号，`6` 是目标状态编号。键为 `0、3、4`，因为只选用了这三个事件，没有要求从 `0` 连续排列。

```cpp
transitions_[3][4] // 当前idle，发生wake_detected，查到speaking的编号6
```

全部注册完成后，表中的整数对应关系如下。每一项 `事件→目标` 都表示内层表中的一个键值对；展示顺序不代表容器遍历顺序。

| 外层键：当前状态 | 内层表：事件编号 → 目标状态编号 |
| --- | --- |
| `0 fault` | `0→0，1→3，3→2` |
| `1 startup` | `0→0，2→3，3→2` |
| `2 stopping` | `0→0，3→2` |
| `3 idle` | `0→0，3→2，4→6` |
| `4 listening` | `0→0，3→2，5→3，7→5` |
| `5 thinking` | `0→0，3→2，8→6` |
| `6 speaking` | `0→0，3→2，9→4，10→3` |

## 4. RegisterTransition 为什么有 -1 和 for 循环

函数见 [StateMachine.cc 第30行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.cc:30)：

```cpp
void StateMachine::RegisterTransition(int from, int event, int to) {
    if (from == -1) {
        for (auto& state : stateActions_) {
            transitions_[state.first][event] = to;
        }
    } else {
        transitions_[from][event] = to;
    }
}
```

`from` 是当前状态编号，`event` 是事件编号，`to` 是目标状态编号。`-1` 是项目约定的“适用于所有已注册状态”，不是第八个 `AppState`。

循环中的 `state` 是外层哈希表中的一项，`state.first` 是状态编号，`state.second` 才是那一对回调。这里的 `state.first` 与 `stateActions_[编号].first` 的层次不同，后者才是进入回调。

第34行逐个为所有已注册状态添加相同规则。当前用于：

| 注册位置 | 批量添加的规则 |
| --- | --- |
| [StateConfig.cc:52](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/StateConfig.cc:52) | 任意已注册状态 + `fault_happen` → `fault` |
| [StateConfig.cc:53](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/StateConfig.cc:53) | 任意已注册状态 + `to_stop` → `stopping` |

这些规则也覆盖 `fault`、`stopping` 自身；`stopping` 进入后会让主事件循环退出，因此表中的规则不等于运行时一定会再次触发。注册时的循环只保存规则，不产生事件、不执行切换。`from=-1` 的作用在注册阶段完成，所以后续查表不需要再判断 `-1`。

## 5. 事件怎样从队列到达状态机

### 5.1 Enqueue、front、pop 和 event_opt

[EventQueue.h 第34行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Events/EventQueue.h:34) 定义 `std::queue<T> queue_;`。这是 `EventQueue<T>` 对象内部的成员变量。成员函数中的 `queue_` 等价于 `this->queue_`。

`Application` 持有的队列是 `EventQueue<int> eventQueue_;`，见 [Application.h 第30行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/Application.h:30)，所以这里保存的是事件整数编号。

| 操作 | 位置 | 含义 |
| --- | --- | --- |
| `queue_.push(event)` | [EventQueue.h:15](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Events/EventQueue.h:15) | 把事件放到队尾 |
| `cond_var_.wait(...)` | [第22行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Events/EventQueue.h:22) | 队列为空时等待，有事件后继续 |
| `T event = queue_.front();` | [第23行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Events/EventQueue.h:23) | 读取并复制队首元素，队列不变 |
| `queue_.pop();` | [第24行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Events/EventQueue.h:24) | 删除队首元素，不返回它的值 |
| `return event;` | [第25行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Events/EventQueue.h:25) | 返回之前保存的事件，包装成 `std::optional<T>` |

例如队列是 `[4,7,9]`，`front()` 后 `event=4`，队列仍为 `[4,7,9]`；`pop()` 后队列变为 `[7,9]`，局部变量 `event` 仍保存 `4`。

[Application.cc 第43行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/Application.cc:43)：

```cpp
if (auto event_opt = eventQueue_.Dequeue(); event_opt) {
    client_state_.HandleEvent(event_opt.value());
}
```

`event_opt` 是接收返回结果的局部变量，类型为 `std::optional<int>`。分号前执行出队，分号后检查是否有值；`.value()` 取出事件编号。本项目的 `Dequeue()` 在空队列时阻塞等待，正常返回时携带事件值，并没有空队列直接返回 `nullopt` 的分支。

### 5.2 HandleEvent 查什么

核心代码位于 [StateMachine.cc 第54行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.cc:54)（节选，省略日志）：

```cpp
auto& possibleTransitions = transitions_[currentState_];
if (possibleTransitions.find(event) == possibleTransitions.end()) {
    return false;
}
int nextState = possibleTransitions[event];
ChangeState(nextState);
return true;
```

`possibleTransitions` 的类型是 `std::unordered_map<int, int>&`，引用整张内层表，没有复制它。`possibleTransitions[event]` 才是表中的目标状态编号。

当前 `currentState_=3`、`event=4` 时，读取过程是：

```text
transitions_[3] → idle的整张内层表
possibleTransitions[4] → 6
nextState = 6
ChangeState(6)
```

`find()` 返回一个迭代器，即元素的位置标记。未找到时返回 `end()`；`end()` 表示最后一个元素之后的位置，不是最后一个元素本身。

所以第56行的 `== end()` 表示没有规则，返回 `false`；初始化时 [第20行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/StateMachine/StateMachine.cc:20) 的 `!= end()` 表示当前状态有注册回调。`true` 表示事件已按规则处理；没有匹配规则时保持原状态。

## 6. Enter、Run、Exit 分别是谁调用的

| 函数 | 职责 | 调用来源 |
| --- | --- | --- |
| `Enter(app)` | 每次进入状态时准备资源、报告状态，按需启动工作线程 | `Initialize()` 或 `ChangeState()` 调用注册的进入回调 |
| `Run(app)` | 在状态工作线程中循环处理任务 | 状态自己的 `Enter()` 创建线程调用 |
| `Exit(app)` | 每次离开状态时停止工作、清理资源，等待线程结束 | `ChangeState()` 调用注册的退出回调 |

例如 [Speaking.cc 第17行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/UserStates/Speaking.cc:17)：

```cpp
state_running_thread_ = std::thread([app]() { Run(app); });
```

状态机只注册 `Enter/Exit`，没有注册 `Run`。这些都是项目自己定义的普通函数名，C++不会根据名字自动执行它们。并非每个状态都需要 `Run`：例如 [Thinking.cc 第4行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/UserStates/Thinking.cc:4) 进入时报告状态，随后等待事件，没有本地工作循环。

在本项目中，`Enter/Exit` 在状态线程执行，各状态的 `Run` 在其工作线程执行。`Speaking::Exit()` 第50行会 `join()` 等待工作线程；由 `Run()` 只发事件、状态线程负责切换，可以避免工作线程直接切换后等待自己结束。

`Application` 的 `client_state_` 是成员对象，声明在 [Application.h 第29行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/Application.h:29)。构造 `Application` 时，成员初始化列表先构造它，再执行构造函数体。普通非静态成员函数可以直接访问当前对象的成员变量，例如 `currentState_` 等价于 `this->currentState_`；局部变量则受所在作用域限制。

### 首条音频标志是否区分唤醒音频和回复音频

这个标志用于区分“本轮第一条回复二进制消息”和“本轮后续消息”，让 `speaking_msg_received` 每轮只发送一次。

```cpp
// WS_Handler.cc 第48行起：二进制消息分支
if (app->get_first_audio_msg_received() == true) {
    app->set_first_audio_msg_received(false);
    app->eventQueue_.Enqueue(
        static_cast<int>(AppEvent::speaking_msg_received)
    );
}
```

本地唤醒提示音由 `Idle::Exit()` 直接加入播放队列，不经过这里，所以不靠这个标志区分本地提示音和服务端回复。下一轮进入listening时再次置true。注意实际检查发生在解包之前，第58行才开始解包。

### get_dialogue_completed 是否在所有声音播完后才设置

`get_dialogue_completed()` 只读取值，定义在 [Application.h 第53行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Client/Application/Application.h:53)。设置为true的动作是 `set_dialogue_completed(true)`。

服务端在 [service_manager.py 第89行](/home/mango/ai/Echo-Mate/Demo/AIChat_demo/Server/service_manager.py:89) 识别到 `exit_chat`，第95行将 `{"type":"chat","dialogue":"end"}` 入发送队列。客户端收到后，在 `WS_Handler.cc` 第116行置true，最后一段回复音频此时可能还没播完。

`Speaking::Run()` 先在第25行检查TTS与播放队列，再在第28行读取对话标志，决定发送 `speaking_end` 还是 `dialogue_end`，最后第35、36行复位两个完成标志。

## 12. 复习时先记住这几条对应关系

| 容易混淆的内容 | 准确含义 |
| --- | --- |
| `AppState` / `AppEvent` | 当前阶段 / 发生的事情 |
| `stateActions_` / `transitions_` | 保存回调 / 保存切换规则 |
| `stateActions_[state].first` / `.first()` | 取出进入回调 / 执行进入回调 |
| `possibleTransitions` / `possibleTransitions[event]` | 整张内层表的引用 / 一个目标状态编号 |
| `RegisterTransition()` / `HandleEvent()` | 提前保存规则 / 事件到来后查规则 |
| `HandleEvent()` / `ChangeState()` | 决定目标状态 / 实际执行Exit、更新、Enter |
| `queue_.front()` / `queue_.pop()` | 读取队首 / 删除队首 |
| `Initialize()` / `startup_done` | 调用startup进入回调 / 触发startup转idle |
| 本地提示音 / 服务端回复 | 两种PCM来源，共用播放队列和speaking状态 |
