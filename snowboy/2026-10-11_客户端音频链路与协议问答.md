# 客户端音频链路与协议问答

本文根据项目 `Demo/AIChat_demo/Client` 的实现，整理从麦克风采集、PCM 队列、Opus 编解码、WebSocket 传输，到服务端 VAD 和状态切换的关键问题。

## 一、录音采集

### 1. `recordCallback` 是库中的方法吗？

不是。`recordCallback` 是项目在 `AudioProcess.h/.cc` 中自己定义的函数，但由 PortAudio 库负责调用。

注册位置在 `AudioProcess::startRecording()`：

```cpp
Pa_OpenStream(
    &recordStream,
    &inputParameters,
    nullptr,
    sample_rate,
    sample_rate / 1000 * frame_duration_ms,
    paClipOff,
    recordCallback,
    this
);
```

`recordCallback` 作为函数指针传给 PortAudio。录音流准备好一块数据后，PortAudio 会自动调用它。

### 2. `inputBuffer` 的值是谁赋予的？

`inputBuffer` 是 `recordCallback()` 的第一个参数。它不是回调函数自己读取出来的，而是 PortAudio 调用回调时传入的地址。

可以把 PortAudio 的内部过程理解为：

```cpp
int16_t pcmBuffer[640];
// 音频设备和驱动把采样数据写入 pcmBuffer
recordCallback(pcmBuffer, nullptr, 640, &timeInfo, flags, userData);
```

实际的采集过程由音频硬件、驱动和 PortAudio 完成。`inputBuffer` 指向 PortAudio 提供的临时 PCM 缓冲区，代码再把它转换为 `const int16_t*` 使用：

```cpp
const int16_t* input = static_cast<const int16_t*>(inputBuffer);
```

### 3. 是检测到声音才调用 `recordCallback` 吗？

不是。录音流启动后，只要准备好一块音频数据，PortAudio 就会调用一次回调；即使没有人说话，也会调用，数据通常是静音或背景噪声。

默认配置为：

```text
采样率：16000 Hz
单声道：1
每次：40 ms
采样帧数：16000 × 40 / 1000 = 640
```

因此通常约每 40 ms 调用一次 `recordCallback()`。

### 4. `Pa_StartStream(recordStream)` 会一直卡在录音吗？

不会。`Pa_StartStream()` 启动 PortAudio 音频流后就返回，持续采集和回调由 PortAudio 管理的后台机制完成。当前线程可以继续执行后面的代码，直到以后调用 `Pa_StopStream()` 停止录音。

这不是项目使用 `std::thread` 创建的录音线程，而是 PortAudio 内部负责调度回调。

### 5. 为什么把 `inputBuffer` 复制到 `recordedAudioQueue`？

`inputBuffer` 是 PortAudio 的临时缓冲区，回调结束后可能被下一次回调复用，不能长期保存它的地址。因此回调中会复制出项目自己拥有的 `frame`：

```cpp
std::vector<int16_t> frame(framesPerBuffer * audioProcess->channels);
std::copy(input,
          input + framesPerBuffer * audioProcess->channels,
          frame.begin());
audioProcess->recordedAudioQueue.push(frame);
```

`recordedAudioQueue` 是应用层的第二级缓冲区，主要用来：

- 保存已经采集好的多块 PCM；
- 把 PortAudio 的采集节奏和编码、网络发送等处理解耦；
- 让回调快速返回，避免在回调中执行耗时操作；
- 在线程之间传递音频数据。

它不只是因为“采集速度太快”，而是为了吸收采集速度和处理速度之间的差异。

### 6. 为什么队列满时使用 `750`？

回调中有：

```cpp
if (audioProcess->recordedAudioQueue.size() >= 750) {
    audioProcess->recordedAudioQueue.pop();
}
audioProcess->recordedAudioQueue.push(frame);
```

`750` 是人为设置的最大音频块数，不是 PortAudio 或 Opus 的特殊要求。默认每块 40 ms，所以约能缓存：

```text
750 × 40 ms = 30000 ms = 30 秒
```

单声道、16 kHz、16 位采样时，30 秒 PCM 约占 960 KB，不包括容器开销。达到上限后丢弃最旧的一块，避免队列无限增长。代码没有说明为什么选择恰好 750。

### 7. `recordedAudioCV` 是什么？

`recordedAudioCV` 是 `std::condition_variable`，不保存音频，只负责协调等待和唤醒。

读取函数中：

```cpp
recordedAudioCV.wait(lock, [this] {
    return !recordedAudioQueue.empty() || !isRecording;
});
```

队列为空且仍在录音时，读取线程睡眠等待；回调放入新数据后：

```cpp
recordedAudioCV.notify_one();
```

通知一个等待线程。这样读取线程不用持续轮询队列，减少 CPU 空转。

### 8. `recordedData` 中每个元素是什么意思？

`getRecordedAudio(std::vector<int16_t>& recordedData)` 取出一块 PCM 音频。每个 `int16_t` 是一个采样点的振幅，范围通常为 `-32768` 到 `32767`。

默认单声道、16 kHz、40 ms 时，一块通常有 640 个采样值：

```text
recordedData[0]：第一个采样点
recordedData[1]：第二个采样点
...
recordedData[639]：最后一个采样点
```

相邻采样点间隔为 `1 / 16000` 秒，即 62.5 微秒。

`recordedData.swap(recordedAudioQueue.front())` 将队首音频容器与输出参数交换，避免逐元素复制；随后 `pop()` 移除队首。

## 二、Listening 状态和清空队列

### 9. `ListeningState::Enter()` 中的操作按顺序执行吗？

按顺序执行，但 `startRecording()` 启动后会立即返回。代码顺序是：

```cpp
app->ws_client_.SendText(json_message);
app->set_first_audio_msg_received(true);
app->audio_processor_.startRecording();
std::this_thread::sleep_for(std::chrono::milliseconds(500));
app->audio_processor_.clearRecordedAudioQueue();
state_running_.store(true);
state_running_thread_ = std::thread([app]() { Run(app); });
```

执行 `sleep_for(500 ms)` 时，PortAudio 仍然在后台采集并调用 `recordCallback()`。500 ms 后清空队列，再启动 `ListeningState::Run()` 线程进行编码和发送。

### 10. 为什么清空 `recordedAudioQueue`？不是一直在采集吗？

是的，录音流启动后会持续采集。这里的“本轮”是指当前一次 `ListeningState` 会话，而不是说麦克风只采集一次。

清空队列会丢弃：

- 上一个状态可能残留的旧音频；
- `ListeningState` 启动后 500 ms 内积累、但尚未开始发送的音频。

清空后，`recordCallback()` 仍会继续入队，`Run()` 从清空之后的队列数据开始逐块编码和发送。

这是一种简单的会话边界处理，但也意味着用户如果在这 500 ms 内开始说话，开头语音可能被丢弃。代码没有说明 500 ms 的精确依据。

### 11. `clearRecordedAudioQueue()` 如何保证安全？

实现使用互斥锁交换队列：

```cpp
void AudioProcess::clearRecordedAudioQueue() {
    std::lock_guard<std::mutex> lock(recordedAudioMutex);
    std::queue<std::vector<int16_t>> empty;
    std::swap(recordedAudioQueue, empty);
}
```

这样清空期间，回调线程不能同时修改录音队列；函数结束时局部的 `empty` 被销毁，原来的音频数据也被释放。

## 三、发送、服务端 VAD 和状态切换

### 12. `ListeningState::Run()` 是整轮录完后再打包吗？

不是。它在循环中逐块处理：

```text
取出一块 PCM
    ↓
Opus 编码
    ↓
添加协议头
    ↓
WebSocket 发送
```

默认每块约 40 ms，用户说话的同时音频就会被连续发送。客户端不会等待整段对话录完再发送。

### 13. 无语音超时在哪里判断？

无语音超时由服务端 VAD 判断，不在客户端 `ListeningState::Run()` 中判断。

`Server/models/vad_model.py` 默认配置：

```python
no_speech_timeout_ms = 3000
```

当当前没有语音，且距离最后一次语音活动超过 3000 ms 时：

```python
if not self.is_speaking and \
   (audio_length - self.last_speech_pos) > self.no_speech_timeout_ms:
    return 2
```

服务端收到返回值 `2` 后发送：

```json
{"type": "vad", "state": "no_speech"}
```

客户端 `WSHandler::handle_vad_message()` 收到后压入 `AppEvent::vad_no_speech`，状态机执行：

```text
listening + vad_no_speech → idle
```

客户端源码中的 `// need a time out` 目前只是注释，还没有实现本地超时。如果网络不再收到音频，服务端的音频时长计时也不会继续推进。

### 14. `WSHandler::handle_vad_message()` 专门处理无语音吗？

目前是的。它读取 JSON 中的 `state`，只有在值为 `"no_speech"` 时才压入 `vad_no_speech` 事件。真正进行语音活动检测和 3 秒超时判断的是服务端 `VADModel`。

## 四、Opus 编码和解码

### 15. 为什么要调用 `initializeOpus()`？

`opus_encode()` 和 `opus_decode()` 需要已经创建并初始化的编码器、解码器状态。构造函数中会调用：

```cpp
encoder = opus_encoder_create(
    sample_rate,
    channels,
    OPUS_APPLICATION_VOIP,
    &error
);
decoder = opus_decoder_create(sample_rate, channels, &error);
```

初始化会分配内部状态并设置采样率、声道数和应用模式。之后每个音频块复用同一个编码器和解码器，析构时由 `cleanupOpus()` 销毁。

如果没有初始化，`encode()` 和 `decode()` 会发现指针为空并返回失败；即使不做空指针检查，直接调用也会产生错误。

### 16. `opus_encode()` 来自哪里？

项目通过：

```cpp
#include <opus/opus.h>
```

获得函数声明。当前 SDK 中的头文件是：

```text
SDK/rv1106-sdk/tools/linux/toolchain/arm-rockchip830-linux-uclibcgnueabihf/arm-rockchip830-linux-uclibcgnueabihf/sysroot/usr/include/opus/opus.h
```

CMake 使用：

```cmake
pkg_check_modules(OPUS REQUIRED opus)
target_link_libraries(AIChatCore ${OPUS_LIBRARIES})
```

头文件提供声明，`libopus.so` 或 `libopus.a` 提供实现。编译阶段检查函数声明和参数，链接阶段由 `-lopus` 找到实际实现。

### 17. 为什么 VSCode 不能跳到 `opus_encode()` 的真正定义？

系统安装的开发包通常包含头文件和已编译库，不包含 Opus 的实现源码。因此 VSCode 只能跳转到 `opus.h` 中的声明，不能跳到库内部实现。

查看 API 时可使用 `Ctrl + 鼠标左键`、`F12` 或悬停提示；要查看算法实现，需要另外获取 Opus 源码，例如：

```bash
apt source opus
```

### 18. `opus_encode()` 的最大字节数是 2048 吗？

调用中：

```cpp
opus_encode(encoder, pcm_frame.data(), frame_size,
            opus_data, 2048);
```

`2048` 表示输出缓冲区最多允许写入 2048 字节，不代表每次编码结果一定是 2048 字节。函数返回实际写入的字节数，并保存到 `opus_data_size`。

当前代码有一个需要注意的问题：`ListeningState::Run()` 中声明的是：

```cpp
uint8_t opus_data[1536];
```

但 `encode()` 告诉 Opus 输出缓冲区容量是 2048 字节。两者不一致，存在潜在越界风险。应统一为至少 2048 字节，或让 `encode()` 接收实际缓冲区容量。

## 五、播放和播放队列

### 19. 客户端在哪里解码服务端音频？

在 `WS_Handler.cc` 收到二进制消息后：

```cpp
UnpackBinFrame(..., opus_data);
audio_processor_.decode(opus_data.data(), opus_data.size(), pcm_data);
audio_processor_.addFrameToPlaybackQueue(pcm_data);
```

真正的 Opus 解码在 `AudioProcess::decode()` 中调用：

```cpp
opus_decode(decoder, opus_data, opus_data_size,
            pcm_frame.data(), frame_size, 0);
```

解码得到 PCM 后进入 `playbackQueue`，等待 PortAudio 播放。

### 20. 播放是否也有第二级缓冲区？

有。播放队列是：

```cpp
std::queue<std::vector<int16_t>> playbackQueue;
```

播放数据链路为：

```text
收到 Opus
    ↓
解码为 PCM
    ↓
addFrameToPlaybackQueue()
    ↓
playbackQueue
    ↓
playCallback()
    ↓
PortAudio 的 outputBuffer
    ↓
扬声器
```

`playbackQueue` 没有设置固定最大容量。网络接收速度长期快于播放速度时，队列可能持续增长。

### 21. `addFrameToPlaybackQueue()` 中每块大小是多少？

默认计算为：

```cpp
int frame_size = sample_rate / 1000 * frame_duration_ms;
```

即 `16000 / 1000 * 40 = 640` 个采样值。若传入 PCM 小于 640 个采样值，会补零到 640；如果大于或等于 640，则直接入队，不会截断。

注意，`playbackQueue.size()` 表示音频块数，不是字节数。队列没有固定的总大小，取决于当前积压了多少块。

### 22. 为什么 `clearPlaybackAudioQueue()` 要加锁？

播放队列至少会被三个线程或执行上下文访问：

- 网络线程调用 `addFrameToPlaybackQueue()` 入队；
- PortAudio 播放回调 `playCallback()` 读取并删除队首；
- 状态退出时调用 `clearPlaybackAudioQueue()` 清空。

因此清空时必须使用同一把 `playbackMutex`：

```cpp
std::lock_guard<std::mutex> lock(playbackMutex);
```

否则可能在 `playCallback()` 读取 `front()` 的同时清空队列，造成数据竞争、失效引用或崩溃。

### 23. `playCallback()` 的参数从哪里来？

和录音回调一样，项目不直接调用 `playCallback()`，而是在 `Pa_OpenStream()` 中注册函数地址：

```cpp
Pa_OpenStream(
    &playbackStream,
    nullptr,
    &outputParameters,
    sample_rate,
    sample_rate / 1000 * frame_duration_ms,
    paClipOff,
    playCallback,
    this
);
```

PortAudio 播放需要数据时，自动按规定的顺序传入参数。参数名不需要相同，但返回值、参数类型和参数顺序必须符合 PortAudio 的回调签名。

### 24. `outputBuffer` 的大小是 40 ms 吗？

`outputBuffer` 指针本身不携带大小。可写入的采样数量由：

```cpp
framesPerBuffer * channels
```

决定。当前默认配置下是：

```text
640 个采样帧 × 1 声道 = 640 个 int16_t
640 × 2 字节 = 1280 字节
```

即约 40 ms。这个大小来自 `startPlaying()` 中对 `Pa_OpenStream()` 的配置，播放流需要单独设置，不是自动从录音流继承；本项目只是使用了相同的参数。

## 六、二进制协议和服务端消息

### 25. 收到的音频包是一个整体吗？

每条 WebSocket 二进制消息是一个完整的协议包，结构为：

```text
[version: 2 字节]
[type: 2 字节]
[payload_size: 4 字节]
[payload: Opus 数据]
```

这代表一条音频消息，不代表整段对话的全部音频。整段语音通常由多条消息组成。

`UnpackBinFrame()` 先读取 8 字节协议头，再根据 `payload_size` 提取 Opus 数据：

```cpp
opus_data.insert(
    opus_data.end(),
    packed_data + 8,
    packed_data + 8 + payload_size
);
```

`insert(first, last)` 使用半开区间 `[first, last)`，因此复制的字节数正好是 `payload_size`。

### 26. 为什么协议头要设置 `ws_protocolVersion`？

它是通信协议版本标记，用来让双方确认二进制包的格式是否兼容。打包时使用网络字节序：

```cpp
pack->version = htons(ws_protocol_version);
```

解析时还原：

```cpp
uint16_t version = ntohs(*version_ptr);
```

客户端收到包后会检查版本和类型：

```cpp
if (protocol_info.version == app->get_ws_protocolVersion() &&
    protocol_info.type == 0) {
    // 解码音频
}
```

### 27. 协议版本 1 和 2 有什么不同？

当前仓库没有分别实现协议 1 和协议 2 的解析逻辑。版本号目前只用于匹配和拒绝不兼容的客户端或音频包。

当前客户端和服务端都配置为 `2`。如果一端使用 `1`、另一端使用 `2`，连接鉴权或音频包校验会失败。

只有将来明确增加类似下面的分支时，版本 1 和 2 才代表不同格式：

```cpp
if (version == 1) {
    // 按协议 1 解析
} else if (version == 2) {
    // 按协议 2 解析
}
```

### 28. 服务端发给客户端的消息长什么样？

服务端发给客户端的消息主要有 JSON 文本和二进制音频两类。

常见 JSON 消息：

```json
{"type": "vad", "state": "no_speech"}
```

无语音超时，客户端产生 `vad_no_speech`。

```json
{"type": "asr", "text": "今天天气怎么样"}
```

语音识别完成，客户端产生 `asr_received`。

```json
{"type": "tts", "state": "end"}
```

服务端 TTS 生成完成，客户端设置 `tts_completed = true`。

```json
{"type": "chat", "dialogue": "end"}
```

服务端判断整个对话结束，客户端设置 `dialogue_completed = true`。

此外，服务端可能发送带有 `function_call` 对象的 JSON，客户端交给意图处理逻辑。

二进制音频消息使用前面所述的 8 字节协议头加 Opus payload。客户端拆包、解码后，把 PCM 放入播放队列。

## 七、`dialogue_end` 和播放结束

### 29. `dialogue_end` 是谁发出的？

服务端不会直接发送名为 `dialogue_end` 的客户端事件。服务端只发送：

```json
{"type": "chat", "dialogue": "end"}
```

客户端的 `WSHandler::handle_chat_message()` 收到后设置：

```cpp
app->set_dialogue_completed(true);
```

然后 `SpeakingState::Run()` 等待 TTS 播放完成和播放队列为空，再由客户端压入：

```cpp
AppEvent::dialogue_end
```

状态机配置为：

```text
speaking + dialogue_end → idle
```

如果 `dialogue_completed` 为 `false`，播放完成后压入的是 `speaking_end`，状态机会回到 `listening` 继续听用户说话。

### 30. 为什么不收到 `dialogue: end` 就直接压入 `dialogue_end`？

收到 `dialogue: end` 时，最后一句 TTS 音频可能还没有播放完。如果立即切换到 `idle`，`SpeakingState::Exit()` 会清空播放队列并停止播放，可能截断最后的语音。

因此当前设计是：

```text
收到 dialogue: end
    ↓
设置 dialogue_completed = true
    ↓
继续播放最后的 TTS
    ↓
播放完成后再压入 dialogue_end
    ↓
speaking → idle
```

### 31. `SpeakingState::Run()` 中为什么有两个 500 ms 延时？

第一处：

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(500));
```

位于循环开头，用于每 500 ms 检查一次 TTS 是否完成和播放队列是否为空，避免检查线程忙等。播放本身仍由 PortAudio 继续进行。

第二处位于检测到播放队列为空之后：

```cpp
if (app->get_tts_completed() &&
    app->audio_processor_.playbackQueueIsEmpty()) {
    std::this_thread::sleep_for(std::chrono::milliseconds(500));
}
```

队列为空只表示 PCM 已经从应用队列取走，最后一块数据可能仍在 PortAudio 或声卡硬件缓冲区中。因此额外等待 500 ms 是为了给播放尾部留时间，但它不是精确查询硬件播放完成状态的机制，代码也没有说明为什么选择 500 ms。

## 八、VSCode、头文件和链接

### 32. 如何在 Linux 中查找 Opus？

```bash
pkg-config --modversion opus
pkg-config --cflags --libs opus
find /usr /usr/local -name opus.h 2>/dev/null
find /usr /usr/local -name 'libopus*' 2>/dev/null
ldconfig -p | grep opus
```

例如输出：

```text
1.3.1
-I/usr/include/opus -lopus
```

说明系统已安装 Opus 1.3.1，编译器可找到头文件，链接器可使用 `libopus`。

### 33. `#include <opus/opus.h>` 在头文件中，`.cc` 文件没有重复声明，为什么仍可使用？

因为 `AudioProcess.cc` 包含了 `AudioProcess.h`：

```text
AudioProcess.cc
    ↓
AudioProcess.h
    ↓
opus/opus.h
```

因此当前翻译单元可以看到 `opus_encode()` 的声明。`.c` 或 `.cc` 文件也可以直接写：

```cpp
#include <opus/opus.h>
```

不需要手工重新声明。

### 34. VSCode 中如何配置 Opus 头文件？

项目已经在 CMake 中通过 `pkg_check_modules(OPUS REQUIRED opus)` 配置编译。若 VSCode 的 IntelliSense 找不到头文件，可以在 `.vscode/c_cpp_properties.json` 的 `includePath` 中加入：

```json
"/usr/include"
```

代码是：

```cpp
#include <opus/opus.h>
```

所以通常添加 `/usr/include`，而不是只添加 `/usr/include/opus`。ARM 交叉编译时，还要确认 SDK sysroot 中存在对应的 `usr/include/opus/opus.h` 和 `libopus`。

### 35. 编译时是根据头文件链接库吗？

不是只根据头文件链接。编译和链接是两个阶段：

```text
源代码 + 头文件 → 编译器 → .o 目标文件
.o + libopus.so/libopus.a → 链接器 → 可执行文件
```

- `opus.h` 提供函数声明，帮助编译器检查参数和返回值；
- `libopus.so` 或 `libopus.a` 提供函数实现；
- CMake 的 `${OPUS_LIBRARIES}` 最终通常对应 `-lopus`。

只有头文件没有库，会出现 `undefined reference to opus_encode`；只有库没有头文件，则会在编译阶段找不到 `opus/opus.h`。
